01 · SPELLBOOK ENGINEERING

130종구현한 카드

데이터 주도 카드 효과 엔진 구축

  • 130종의 카드마다 스크립트를 개별 작성하는 대신, 28종의 효과 타입과 20종 이상의 상태이상, 7종의 조건절을 모듈화한 공통 연산 엔진을 구축했습니다.
  • [C# 스크립트 작성 → 컴파일 → 씬 연결]의 과정을 [CSV 데이터 1행 추가] 한 단계로 단축했습니다.

네트워크 동기화 및 아키텍처 설계

  • Unity NGO 모듈로 로비 생성과 실시간 인게임 흐름을 제어하고, 클라이언트 변조를 막기 위해 서버 권위 모델을 구현했습니다.
  • '클라이언트(플레이어) – 게임 서버 – 웹 서버'로 이어지는 3계층 통신 아키텍처를 설계하고 구현했습니다.

음성 녹음 및 사운드 파이프라인

  • Unity Microphone System으로 플레이어의 음성 영창을 녹음해 웹 서버로 패킷을 제출하는 파이프라인을 구축하고, 인게임 사운드(BGM/SFX) 제어 매니저를 구현했습니다.

03 · BOSS FIGHTS: LATENCY & NETCODE

단일 API 의존의 한계 인지와 최적화 방향 도출

ISSUE
음성 원본을 멀티모달 LLM에 한 번에 보내 창의성과 몰입도를 동시에 평가하는 구조였습니다. 경량 모델(Gemini 2.5 Flash)은 음성 인식 정확도가 떨어져 문맥을 온전히 판별하지 못했고, 대형 모델(GPT-4o Audio)은 추론 시간이 길어 실시간성이 훼손됐으며 예산상 도입도 어려웠습니다.
DECISION
데이터를 목적에 맞게 나누는 2-Track 파이프라인을 도출했습니다. 창의성(문맥)은 클라이언트에서 STT로 텍스트화해 가벼운 페이로드만 LLM에 요청하고, 몰입도(감정)는 주파수·진폭 등 음향 피처를 자체 분석합니다.
RESULT
완성된 외부 API에 통째로 의존할 때 생기는 퍼포먼스 병목을 체감했고, 차기 유지보수 목표로 데이터 특성에 맞춰 파이프라인을 분리하고 지연 시간을 최소화하는 구조를 잡았습니다.

네트워크 환경의 한계

ISSUE
서버 권위 모델을 설계했지만 비용과 구조적 한계로 호스트가 서버를 겸하는 Listen Server를 채택해, 호스트 PC가 조작되면 서버 전체가 노출되는 보안 한계가 남았습니다. 또한 ParrelSync로 단일 PC에서 다중 클라이언트를 검증해 실제 네트워크 지연을 온전히 체감하지 못했습니다.
DECISION
보안과 지연 문제의 원인을 개발 환경 구조에서 찾아 정리했습니다.
RESULT
다음 프로젝트에서는 클라이언트와 물리적으로 분리된 전용 서버(Dedicated Server)를 구축하고, 지연 보상 예측(Prediction)과 실제 통신 환경 최적화를 다뤄보고자 합니다.
