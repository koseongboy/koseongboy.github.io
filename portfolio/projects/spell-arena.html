데이터 주도 카드 효과 엔진 구축

  • 130종의 카드마다 스크립트를 개별 작성하는 대신, 28종의 효과 타입과 20종 이상의 상태이상, 7종의 조건절을 모듈화한 공통 연산 엔진을 구축했습니다.

02 · TROUBLESHOOTING

기획 팀원과 병렬로 진행한 카드 효과 데이터화

ISSUE
처음에는 CSV에서 카드 이름 · 설명 텍스트 같은 기본 정보만 읽고, 효과는 카드마다 코드로 따로 구현했습니다. 카드를 추가하거나 효과를 고칠 때마다 코드 작업이 필요해, 기획이 바뀌면 구현이 따라가야만 하는 구조였습니다.
DECISION
기획 팀원과 협력해, 기획 팀원이 정리한 컬럼 구조에 맞춰 각 컬럼이 수행할 커맨드를 정의하고 구현했습니다. 카드는 이 커맨드들을 묶은 매크로 커맨드로 실행됩니다.
RESULT
이미 있는 효과를 조합한 카드는 추가 공수가 15분 이상에서 1분 내외로 줄었고, 기획 팀원이 CSV에 행을 넣는 것만으로 직접 추가할 수 있게 됐습니다.
LEARNED
컬럼 이름이라는 작은 규격을 먼저 합의하니, 서로의 작업이 끝나기를 기다리지 않고 동시에 진행할 수 있었습니다. 팀원의 제안을 실제로 동작하는 구조로 구체화하는 것도 개발자의 역할이라는 것을 배웠습니다.

카드 조합에 따라 바뀌는 동적 효과 처리

ISSUE
'강굽이'처럼 선택한 카드들 중 물 속성이 가장 많을 때 발동하는 효과는, 카드 한 장의 데이터만으로는 값을 정할 수 없었습니다. 커맨드 큐에서 선택한 카드들의 속성을 파악해 각 커맨드에 넣어 주는 방식이라, 이런 효과가 하나 늘 때마다 큐와 여러 커맨드를 함께 고쳐야 할 만큼 변경 범위가 컸습니다.
DECISION
데미지처럼 상황에 따라 값이 바뀌는 효과를 동적 효과 커맨드로 따로 정의해 일반 커맨드와 분리하고, 속성별 동적 효과는 이 커맨드에 추가하도록 정리했습니다.
RESULT
변경 범위를 동적 효과 커맨드 안으로 좁혔습니다. 다만 속성 판별을 분기문으로 처리해, 속성이나 조건이 늘수록 분기가 길어지는 유지보수 문제가 남았습니다.
LEARNED
변경 하나가 커맨드 큐와 여러 커맨드로 번지는 것을 한 번 겪은 뒤로, 새 기능을 넣기 전에 영향 범위를 먼저 예상하고 바뀔 부분을 한곳에 모아 두게 됐습니다.

03 · RETROSPECTIVE

음성 판정 대기와 전송 구조의 한계

CONTEXT
영창 판정은 클라이언트가 녹음한 음성 원본을 웹 서버로 올린 뒤, 서버가 멀티모달 LLM으로 평가를 마칠 때까지 결과를 기다리는 구조였습니다. 판정 중에는 로딩 화면이 떠 있어, 모델의 추론 시간이 곧 플레이어가 기다리는 시간이었습니다. 게다가 사용한 모델(Gemini 2.5 Flash)은 음성 인식이 부정확해, 기다린 만큼 정확한 판정을 얻지도 못했습니다. 외부의 무단 접근 트래픽으로 서버가 불안정해, 판정 기능을 충분히 테스트하지 못한 것도 한계였습니다. 저는 결과를 1초 간격으로 최대 20회 조회(폴링)하고, 끝내 결과가 오지 않으면 기본 점수로 넘어가게 해 서버가 응답하지 않아도 게임이 이어지도록 했습니다.
IDEA
1초 간격의 고정 폴링은 결과가 늦을수록 불필요한 요청만 늘어나므로, 조회 간격을 점점 늘려 가는 방식(지수 백오프)으로 바꾸는 것을 구상했습니다. 또 클라이언트가 더 많은 처리를 맡아 서버로 보내는 데이터를 줄이는 2-Track 구조를 정리했습니다. 문맥(창의성)은 클라이언트에서 STT로 텍스트화해 텍스트만 보내고, 몰입도(감정)는 음량 · 음높이 같은 음향 피처를 클라이언트에서 계산해 수치만 보내는 방식입니다. 프로젝트가 끝난 뒤 정리한 개인 구상으로, 팀에 공유하거나 적용하지는 않았습니다.
LEARNED
판정의 품질과 응답 속도는 서버 모델만의 문제가 아니라, 클라이언트가 무엇을 얼마나 보내느냐에도 달려 있다는 것을 배웠습니다.

무음 · 잡음 입력으로 인한 LLM 환각

CONTEXT
녹음에 소리가 전혀 없으면 진폭이 고정 기준(0.04)을 한 번도 넘지 않는지 확인해 전송하지 않도록 막았습니다. 하지만 화이트 노이즈나 숨소리는 이 기준을 넘어 그대로 판정 서버로 넘어갔고, 모델이 특정 단어를 끝없이 반복하는 환각 현상이 발생했습니다. 고정된 기준 하나로는 거르기 어렵습니다. 마이크마다 감도와 입력 게인이 달라 같은 목소리도 기기마다 측정값(dBFS)이 다르고, 마이크 가까이에서 쉰 숨소리는 작은 목소리만큼 커질 수 있기 때문입니다.
IDEA
녹음 단계에서 잡음만 있는 음성은 전송하지 않는 방법을 고안했습니다. 녹음 시작 전 3 · 2 · 1 카운트다운 동안 주변 소음을 측정해 기기별 소음 기준(noise floor)을 잡고, 녹음된 음성에 소음 기준보다 12dB 이상 큰 구간이 있을 때만 말소리로 보고 서버로 전송하는 방식입니다. 그 구간이 합쳐서 300ms보다 짧으면 전송하지 않습니다. 마감 일정 때문에 구현과 검증은 하지 못했고, 환각 현상은 해결되지 않은 채 프로젝트가 끝났습니다.
LEARNED
서버 · 모델 쪽 문제처럼 보여도, 클라이언트가 보내는 입력의 품질을 먼저 거르면 막을 수 있는 지점이 있다는 것을 배웠습니다. 아이디어는 바로 문서로 남겨야 다음 작업으로 이어질 수 있다는 점도 느꼈습니다.

호스트 권한 구조의 한계

CONTEXT
비용 문제로 별도 서버 없이 호스트가 서버를 겸하는 Listen Server를 택했습니다. 호스트 PC가 조작되면 판정 전체가 노출되는 구조입니다. 또 프로젝트가 끝난 뒤 포트폴리오를 정리하며 코드를 다시 읽다가, 서버가 마나를 차감할 때 클라이언트가 보낸 비용(declaredCost)을 그대로 쓰고 카드 ID로 다시 계산하지 않는다는 것을 발견했습니다. 게스트 클라이언트도 비용을 조작할 수 있는 빈틈입니다. 테스트는 ParrelSync로 한 PC에서 여러 클라이언트를 띄워 진행해, 실제 네트워크 지연은 확인하지 못했습니다.
IDEA
비용은 서버가 받은 카드 ID로 CardDatabase에서 직접 합산해 차감하고, 클라이언트에서는 카드 ID와 대기표만 받도록 바꿉니다. 호스트 변조까지 막으려면 클라이언트와 분리된 전용 서버(Dedicated Server)가 필요하고, 실제 네트워크 환경에서 지연을 측정하는 테스트도 함께 진행해야 합니다.
LEARNED
서버에서 다시 확인한다고 생각한 값 중에도 클라이언트 입력을 그대로 믿는 부분이 남아 있을 수 있다는 것을 알게 됐습니다. 이후로는 서버로 들어오는 값마다 서버가 직접 다시 계산할 수 있는 값인지부터 확인합니다.
