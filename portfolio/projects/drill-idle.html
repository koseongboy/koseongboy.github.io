01 · CORE SYSTEMS

OS 레벨 백그라운드 입력 감지

  • Windows API 저수준 훅(SetWindowsHookEx의 WH_KEYBOARD_LL, WH_MOUSE_LL)으로, 게임 창이 포커스를 잃은 상태에서도 키보드 · 마우스 입력을 받아 공장의 동력으로 바꿨습니다.
  • 훅 콜백에서는 입력을 큐에 넣기만 하고 바로 다음 훅으로 넘긴 뒤, Update()에서 큐를 비우며 입력 횟수를 셉니다. 콜백이 오래 걸리면 시스템 전체의 입력이 느려지기 때문입니다.
  • 훅 콜백 끝에서 CallNextHookEx를 호출해, 다른 프로그램의 입력을 막지 않습니다.

시설 시스템

  • 드릴 · 채굴기 · 연구소 · 가공 시설 등을 공통 FacilityEntity에서 상속해, 각 시설이 자기 생산 동작만 구현하도록 했습니다.
  • 시설은 데이터에 정의된 상대 좌표 목록으로 모양을 가지고 그리드에 배치되며, 배치할 때 시너지가 적용되는 칸을 미리 보여 줍니다.
  • 배치한 시설이 동력을 받아 자동으로 생산하는 흐름을 구현했습니다.

엔진 성장 시스템 (기획 · 구현)

  • 엔진이 레벨업할 때마다 칸 모양이 커지고 색깔별로 진화하는 성장 방식을 제안했습니다. 테트리스 블록처럼 모양이 다른 엔진을 판에 맞춰 배치하는 구조입니다.
  • 엔진 형태 · 스프라이트 · 색상 변경을 구현하고, 엔진은 프리팹 하나와 스프라이트 두 장으로 표현해 종류가 늘어도 프리팹이 늘지 않게 했습니다.
  • 키보드 입력 횟수가 공장의 동력이 되는 게임 루프와, 동력 장치와 생산 장치를 나누는 구조를 기획했습니다.

초기 CSV 데이터 파이프라인

  • 헤더 줄을 키로 삼아 CSV 행을 Dictionary로 바꾸는 파서를 만들어, 컬럼이 바뀌어도 파서 코드를 고치지 않게 했습니다(CSV_Data ↗). CSV와 스프라이트는 Addressables로 비동기 로드하고, 여러 테이블을 Task.WhenAll로 동시에 불러왔습니다.
  • 이후 팀원이 CSV를 ScriptableObject로 자동 변환하는 방식으로 바꿨습니다.

02 · RETROSPECTIVE

전역 키 후킹의 보안 위험

CONTEXT
백그라운드 입력을 받기 위해 쓴 저수준 전역 훅은 키로거와 같은 API라, 백신에 악성 코드로 오탐지될 위험이 있습니다. 게임은 입력 횟수만 쓰고 어떤 키인지는 사용하지 않지만, 훅 콜백에서 키 코드(vkCode)를 읽어 큐에 넣는 코드가 남아 있어 키 값이 잠시 메모리에 올라옵니다. Raw Input(RIDEV_INPUTSINK)으로 바꾸는 것도 검토했지만, 백그라운드 키 입력을 받는다는 점은 같아 오탐 위험이 줄지 않고, 기한 안에 입력 구조를 다시 짜기도 어려워 훅을 유지했습니다.
IDEA
콜백에서 키 코드를 읽지 않고 입력 횟수만 늘리면(Interlocked.Increment), 큐도 필요 없고 키 값이 메모리에 올라오지 않습니다. 오탐 위험은 훅을 쓰는 한 남으므로, 배포한다면 실행 파일 코드 서명과 입력 수집 범위를 알리는 안내가 필요합니다.
LEARNED
입력 API를 바꾸는 것보다, 기능에 필요한 정보가 무엇인지 먼저 정하고 그 이상은 읽지 않는 것이 보안 위험을 줄이는 방법이라는 것을 배웠습니다.
